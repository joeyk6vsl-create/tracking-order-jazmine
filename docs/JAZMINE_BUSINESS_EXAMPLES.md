# A. ราคาและส่วนลด

## A1 — เปอร์เซ็นต์และส่วนลดเงินพร้อมกัน

```text
ราคาสินค้าและส่วนเพิ่ม     1,000,000 LAK
ส่วนลดเปอร์เซ็นต์                10%
ส่วนลดจำนวนเงิน              50,000 LAK
```

คำนวณ:

```text
1,000,000 - 10% = 900,000
900,000 - 50,000 = 850,000
```

ผลที่คาดหวัง:

```text
ราคาสุดท้าย = 850,000 LAK
```

## A2 — ของแถมร่วมกับส่วนลด

```text
ลูกค้าซื้อ 10 ตัว
ได้ของแถม 1 ตัว
ราคาสินค้าที่ซื้อรวม 1,000,000 LAK
ส่วนลด 10%
```

ผลที่คาดหวัง:

```text
จำนวนที่คิดเงิน = 10 ตัว
จำนวนที่ต้องผลิตและส่ง = 11 ตัว
ยอดหลังลด = 900,000 LAK
ของแถม 1 ตัวไม่สร้างของแถมเพิ่ม
```

## A3 — ส่วนลดสูงกว่ายอด

```text
ยอดหลังลดเปอร์เซ็นต์ = 40,000 LAK
ส่วนลดจำนวนเงิน = 50,000 LAK
```

ผลที่คาดหวัง:

```text
ราคาสุดท้าย = 0 LAK
ห้ามเป็น -10,000 LAK
```

# B. การแก้ออเดอร์

## B1 — แก้ก่อนยืนยัน

ผู้ใช้เปลี่ยนไซซ์ จำนวน ผ้า และส่วนลดก่อนยืนยัน

ผลที่คาดหวัง:

- แก้ได้ทั้งหมด
- เมื่อกดบันทึกการเปลี่ยนแปลง ต้องใส่เหตุผล
- ระบบคำนวณราคาใหม่
- ยังไม่มีเลขออเดอร์ถาวรจนกว่าจะยืนยันสำเร็จ

## B2 — หลังยืนยันแล้วราคาสูงขึ้น

```text
ราคาเดิม = 1,000,000 LAK
รับเงินแล้ว = 500,000 LAK
ราคาใหม่ = 1,200,000 LAK
```

ผลที่คาดหวัง:

```text
ยอดคงเหลือ = 700,000 LAK
```

ระบบต้องเก็บราคาเดิม เหตุผล ผู้แก้ และราคาฉบับใหม่

## B3 — จ่ายครบแล้วราคาใหม่ลดลง

```text
ราคาเดิม = 1,000,000 LAK
รับเงินแล้ว = 1,000,000 LAK
ราคาใหม่ = 800,000 LAK
```

ผลที่คาดหวัง:

```text
เงินเกิน = 200,000 LAK
สถานะ = รอจัดการ
```

ระบบห้ามคืนเงินอัตโนมัติ เจ้าของเป็นผู้ตัดสินใจคืนเต็มหรือบางส่วน

## B4 — แก้หลังเริ่มผลิต

เปลี่ยนผ้าหรือส่วนประกอบหลังฝ่ายผลิตเริ่มงานแล้ว

ผลที่คาดหวัง:

- แก้ได้โดยเจ้าของหรือพนักงานแผนก ADMIN
- ต้องใส่เหตุผล
- งานเดิมที่ทำแล้วไม่หาย
- ระบบแจ้งแผนกที่ได้รับผลกระทบ
- ถ้าของเดิมใช้ไม่ได้ ให้บันทึกความเสียหาย
- ถ้าต้องทำใหม่ ให้สร้างงานผลิตทดแทน

# C. การรับเงินและคืนเงิน

## C1 — รับมัดจำ

```text
ราคาออเดอร์ = 1,000,000 LAK
พนักงานแผนก ADMIN เลือกรับมัดจำ = 300,000 LAK
```

ผลที่คาดหวัง:

```text
รับแล้ว = 300,000 LAK
คงเหลือ = 700,000 LAK
```

ไม่มีข้อบังคับว่ามัดจำต้องเป็นเปอร์เซ็นต์เท่าไร

## C2 — บันทึกรับเงินผิด

```text
บันทึกผิด = 500,000 LAK
ยอดที่รับจริง = 50,000 LAK
```

ผลที่คาดหวัง:

1. พนักงานแผนก ADMIN ยกเลิกรายการ 500,000 พร้อมเหตุผล
2. รายการเดิมยังอยู่ในประวัติแต่ไม่นับในยอดรับสุทธิ
3. สร้างรายการใหม่ 50,000
4. ยอดรับสุทธินับ 50,000

## C3 — คืนบางส่วน

```text
รับเงินสุทธิแล้ว = 1,000,000 LAK
เจ้าของคืน = 200,000 LAK
```

ผลที่คาดหวัง:

```text
รับสุทธิหลังคืน = 800,000 LAK
```

ต้องเก็บเหตุผล ผู้คืน วันเวลา และช่องทางคืน ไม่ต้องออกเอกสารคืนเงินให้ลูกค้าใน V1

## C4 — คืนเต็มจำนวน

เจ้าของคืนเงินที่สามารถคืนได้ทั้งหมด

ผลที่คาดหวัง:

- รายการรับเงินเดิมยังอยู่
- รายการคืนเงินแยกออกมา
- ยอดรับสุทธิถูกลดตามยอดคืน
- ประวัติทั้งสองรายการตรวจสอบได้

# D. ปัญหาการผลิต

## D1 — พบปัญหาแต่ทำงานต่อ

พนักงานพบตำหนิเล็กน้อยและเลือก `REPORT_AND_CONTINUE`

ผลที่คาดหวัง:

- บันทึกปัญหา ผู้รายงาน และเวลา
- งานส่วนที่ได้รับอนุญาตยังเดินต่อได้
- ปัญหารอพนักงานแผนก ADMIN หรือเจ้าของตรวจและปิด

## D2 — พบปัญหาและหยุด

พนักงานพบปัญหาที่อาจทำให้เสียหายเพิ่มและเลือก `REPORT_AND_STOP`

ผลที่คาดหวัง:

- งานส่วนที่ได้รับผลกระทบหยุด
- งานส่วนอื่นที่ไม่เกี่ยวข้องไม่จำเป็นต้องหยุดทั้งหมด
- เจ้าของหรือพนักงานแผนก ADMIN เป็นผู้แก้และอนุญาตให้ทำต่อ

## D3 — สินค้ามีตำหนิและต้องผลิตใหม่

```text
สินค้าเสียหาย = ไซซ์ L จำนวน 2 ตัว
```

ผลที่คาดหวัง:

- เก็บข้อมูลของเสีย 2 ตัว
- สร้างงานผลิตทดแทนไซซ์ L จำนวน 2 ตัว
- เชื่อมงานทดแทนกับปัญหาเดิม
- จำนวนพร้อมส่งจะเพิ่มเมื่อของทดแทนผ่านการตรวจแล้ว

# E. การส่งสินค้า

## E1 — ส่งทั้งที่ยังค้างเงิน

```text
ยอดออเดอร์ = 1,000,000 LAK
รับแล้ว = 400,000 LAK
ยอดค้าง = 600,000 LAK
```

ผลที่คาดหวัง:

- ระบบแสดงคำเตือนและยอดค้าง 600,000
- เจ้าของหรือพนักงานแผนก ADMIN ยืนยันการส่งได้
- เก็บยอดค้าง ณ เวลาที่ส่งไว้ในประวัติ

## E2 — ส่งเพียงบางส่วน

```text
พร้อมส่งไซซ์ M = 10 ตัว
ส่งครั้งแรก = 6 ตัว
```

ผลที่คาดหวัง:

```text
ส่งแล้ว = 6 ตัว
ยังส่งได้ = 4 ตัว
```

## E3 — ลูกค้ามารับเอง

ผลที่คาดหวัง:

- วิธีรับสินค้าเป็น `CUSTOMER_PICKUP`
- สถานะ `CONFIRMED` เมื่อสินค้าออกจากร้านกับลูกค้าจริง
- เก็บวันเวลาและผู้ยืนยัน

## E4 — ร้านจัดส่ง

ผลที่คาดหวัง:

- วิธีรับสินค้าเป็น `SHOP_DELIVERY`
- เก็บบริษัทขนส่งและเลขติดตามเมื่อมี
- สถานะ `CONFIRMED` เมื่อสินค้าถูกส่งออกจากร้านจริง

## E5 — เตรียมส่งล่วงหน้า

พนักงานกรอกข้อมูลผู้รับและจำนวนสินค้าไว้ แต่สินค้ายังอยู่ในร้าน

ผลที่คาดหวัง:

```text
สถานะ = PREPARED
จำนวนส่งแล้วไม่เพิ่ม
```

เมื่อผู้มีสิทธิ์ยืนยันส่ง (รวมกรณีตั้งใจยืนยันล่วงหน้าตามคำสั่งเจ้าของ พร้อมบันทึกป้ายและเหตุผล โดยต้องมีจำนวนผ่าน QC พอ) จะเปลี่ยนเป็น:

```text
สถานะ = CONFIRMED
จำนวนส่งแล้วเพิ่ม
```

# F. สกุลเงินและรายงานกำไร

## F1 — รับเงิน THB หรือ USD

เฉพาะเจ้าของกรอกอัตราแลกเปลี่ยน ตัวอย่างนี้ใช้ตัวเลขสมมติเพื่อตรวจวิธีทำงาน ไม่ใช่อัตราจริง:

```text
เจ้าของกำหนด 1 THB = 650 LAK
ลูกค้าจ่าย 1,000 THB
มูลค่าเงินที่รับ = 650,000 LAK
```

ผลที่คาดหวัง:

- เก็บจำนวนเดิม 1,000 THB
- เก็บอัตรา 1 THB = 650 LAK ไว้กับรายการ
- เก็บมูลค่า 650,000 LAK
- ถ้าเจ้าของเปลี่ยนอัตราในวันหลัง รายการนี้ยังคงเป็น 650,000 LAK
- พนักงานแผนก ADMIN รับเงินตามอัตราที่เจ้าของกำหนดได้ แต่เปลี่ยนอัตราไม่ได้

## F2 — รายงานกำไร

สูตรที่ยืนยันแล้ว:

```text
รายได้
- ต้นทุนผ้า
- ค่าแรง
- ค่าน้ำหมึกและวัสดุพิมพ์
- ต้นทุนการผลิตอื่น
= กำไรโดยประมาณ
```

ตัวอย่างขณะที่ข้อมูลยังไม่ครบ:

```text
รายได้ = 1,000,000 LAK
ต้นทุนผ้า = ยังไม่มีข้อมูล
ค่าแรง = ยังไม่มีข้อมูล
ค่าน้ำหมึก = ยังไม่มีข้อมูล
```

ผลที่คาดหวัง:

```text
กำไร = ยังไม่สามารถคำนวณได้ครบ
```

ห้ามแสดงกำไร 1,000,000 LAK โดยถือว่าต้นทุนที่ยังไม่มีข้อมูลเป็นศูนย์

# วิธีตรวจรับ

## G1 — ลูกค้าขาจรไม่เพิ่มรายชื่อประจำ

ADMIN เปิดสร้างออเดอร์ เลือกลูกค้าขาจร กรอกชื่อและเบอร์ แล้วทำออเดอร์จนยืนยัน ผลที่ถูกต้องคือมีประวัติออเดอร์พร้อมชื่อ/เบอร์ที่ค้นได้ แต่จำนวนลูกค้าประจำไม่เพิ่ม

## G2 — เลือกบันทึกเป็นลูกค้าประจำภายหลัง

จากออเดอร์ขาจร เจ้าของหรือ ADMIN เลือกบันทึกเป็นลูกค้าประจำ ผลที่ถูกต้องคือใช้ข้อมูลนั้นเริ่มงานครั้งถัดไปได้ และข้อมูลในออเดอร์เก่าไม่เปลี่ยน

## G3 — เลือกส่วนประกอบด้วยรูป

เลือกปุ่มคอกลมแล้วต้องแสดงชื่อคอกลมและสถานะเลือกแล้ว เมื่อเลือกคอโปโลแทน ต้องเหลือคอที่เลือกเพียงหนึ่งแบบ และหน้าตรวจสอบแสดงคอโปโล

## วิธีตรวจรับตัวอย่าง

เจ้าของตรวจแต่ละตัวอย่างแล้วตอบได้หนึ่งแบบ:

```text
ถูกต้อง
ต้องแก้
ต้องเพิ่มเงื่อนไข
```

เมื่อทุกตัวอย่างได้รับการยืนยัน ให้เปลี่ยนสถานะเอกสารเป็น `LOCKED` และใช้เป็นชุดทดสอบก่อนเปิดระบบจริง
